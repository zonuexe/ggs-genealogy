# 北極星：謄本に書かれたことを失わずに保存し、解釈と区別して積み上げる

用語は [GLOSSARY.md](../../GLOSSARY.md) に従う。

## 出発点

収集者は Gramps で戸籍に基づく系譜情報を管理していた。しかし Gramps の核家族モデルは戸籍の構造（家、戸主、改製、除籍、実親と養親の併記など）に合わず、和暦を西暦に換算して入力したことで原文表記も失われた。結果として、事実を確かめるには毎回元の謄本に戻る必要があった。GGS は、このデータ構造と管理モデルを一から設計し直すために作る。

その先には、戸籍の制度に詳しくない人でも、AI エージェントの助けを借りて気軽に戸籍を集め、系図を作れるようにしたいという狙いがある。GGS はそのための堅牢な土台になる。

## 決定

1. **北極星は記録への忠実さとする。** 謄本の記載を原文表記ごと一つも失わず、機械で検証できる形で長く保存する。可視化や他ツールとの相互運用、気軽に使えることは、その上に乗る価値であり、そのために記録を丸めることはしない。
2. **気軽さは、記録を丸めることではなく、手間を AI エージェントが肩代わりすることで実現する。** 転写を変更しないこと、解釈に確度を付けること、作成者と確認状況を記録することが、AI の誤りを封じ込める仕組みになる。忠実さを下げると AI の誤りと謄本の事実が区別できなくなるので、土台の厳密さは使いやすさの前提である。
3. **主なユーザーは収集者とする。** 収集者は謄本を取得し、自分のデータに最終的に責任を持つ人であり、戸籍の専門知識は問わない。転写や同定は収集者自身が行っても、AI エージェントが行ってもよい。
4. **記録中心のモデルとする。** 一次データは謄本の転写であり、人物は記載人物の同定（根拠を伴う判断）から成り立つ。
   - 戸籍・謄本・記載を区別する。改製の前と後は別の戸籍として扱い、改製で結ぶ。
   - 転写は一度作ったら変更しない。戸籍に新しい記載が加われば、新たに交付された謄本を別の転写として加える。謄本の交付日は必須とする。
   - 部分的な転写を認める。その代わり、謄本ごとに転写状況を明示する。
   - 正規化した値（西暦、新字体など）は、原文表記に加える派生値として扱い、原文表記を置き換えない。原文表記には判読不能箇所、訂正・抹消の痕跡、記載された欄の位置も含める。
5. **戸籍の収集も支援する。** 転写に記載された従前の戸籍や転籍先から、まだ謄本が手元にない戸籍を請求候補として洗い出す。具体的な請求の手続き（どの役所に、どの方法で請求できるか）は AI エージェントの知識に任せ、GGS は請求候補を出すところまでを担う。
6. **対象範囲は日本の戸籍（明治民法から現行法まで）に限る。** 戸籍以外の資料（軍歴照会票など）は範囲外とする。
7. **AI が作ったものも正本に入れてよいが、作成者と確認状況を必ず記録する。** 転写と解釈のそれぞれに、誰が作ったか（収集者、他の人、AI エージェントとそのモデル）と、人が確かめたかどうか（未確認、確認済み、確かめた人）を残す。未確認のものは未確認として区別して扱い、後から詳しい人や別のモデルが見直せるようにする。作成者が誰であっても、転写は SHACL の形式検証を通らなければならない。
8. **利用の窓口は AI エージェントとする。** GGS は、エージェントが呼び出すライブラリと CLI（必要なら MCP サーバー）という土台に徹し、独自の GUI は作らない。Turtle は保存の形式であり、収集者が読む必要はない。
9. **Gramps と Graphviz は可視化のための一方向の出力先とする。** ファンチャートのような表示を得る手段であり、Gramps である必然性はない。既存の `.gramps` データは一度だけ移行し、暫定の同定として扱う。西暦に換算済みで原文表記がないため、事実の根拠にはしない。
10. **ローカルファーストとする。** データは収集者が管理するストレージ（Dropbox、Git など）に置き、GGS が自分から外部へ送信することはない。原本の画像（PDF）は GGS では保管せず、相対パスとハッシュ値で参照する。クラウドの AI エージェントを使うことを選べば、戸籍の内容（存命の人の情報を含む）がそのサービスに送られる。この選択は収集者が行うものとし、エージェント向けの説明では、そのことを収集者に知らせるよう求める。
11. **祖先経路番号は識別子にしない。** 祖先経路番号は収集者を起点とする便宜上のラベルで、起点となる人が変われば値も変わる（収集者の兄弟姉妹にとっては有効だが、子の世代にはずれる）。必要であれば同定の結果から算出して表示する。

## Considered Options

- **結論中心モデル（Gramps / GEDCOM 型）**: 人物と出来事を直接一つのグラフに書く方式。戸籍では同じ人物が転籍・分家・改製のたびに別の記録へ繰り返し現れるため、「何が書かれていたか」と「どう解釈したか」が混ざり、忠実さが崩れる。却下。
- **Gramps と対等に編集し、往復で情報を失わない方式**: 初期の叩き台で必須要件とされていた。Gramps 上の編集は解釈であって転写に戻すことができず、往復で情報を失わない仕組みの維持費も高い。却下。
- **汎用の系譜ツール**: 戸籍に固有の構造（家、改製、除籍）が薄まり、北極星と両立しない。却下。
- **人が確認したものだけを正本に入れる**: 戸籍に詳しくない収集者は AI の転写を謄本と突き合わせて確かめられないので、作業が進まなくなる。作成者と確認状況を記録すれば、未確認のものも区別して扱える。却下。
- **気軽さのために記録を簡略化する**: AI の誤りと謄本の事実が区別できなくなり、土台が成り立たない。却下。
- **GGS 自身が GUI や Web アプリを提供する**: AI エージェントが窓口になれば、GGS は土台の堅牢さに集中できる。却下。

## Consequences

- 今の実装（`koseki.ttl` の人物を中心にしたオントロジー、往復とマージを前提にした `ggs import`）は結論中心の設計であり、記録中心へ移す必要がある。移行の詳細は ADR-0001 と Issue で扱う。
- 初期の叩き台は [docs/archive/initial-handoff.md](../archive/initial-handoff.md) に移した。方針の拠り所は本 ADR に一本化し、叩き台と食い違う場合は本 ADR が優先する。
